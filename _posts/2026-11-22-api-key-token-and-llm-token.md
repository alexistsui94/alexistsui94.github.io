学习 API 和大模型时，有三个概念很容易被混在一起：API Key、Access Token，以及模型处理文本时所说的 Token。

前两者和“身份、权限”有关，后者和“文本如何被切分”有关。把它们混在一起，会让很多教程看起来比实际更复杂。

## 1. API 是什么

可以把 API 理解成系统之间约定好的服务窗口。

调用方不需要知道对方内部所有实现，只要按照约定提供请求方式、地址、参数和身份凭证，就能得到结构化结果。对业务系统来说，这个“结果”可能是客户资料、订单状态，也可能是一段模型生成的文本。

一次典型调用通常包含：

- **URL**：要访问哪个资源；
- **Method**：要做什么，例如 GET 查询、POST 创建；
- **Headers**：身份、内容类型等附加信息；
- **Body**：需要提交的数据；
- **Response**：对方返回的数据和状态码。

JSON 是常见的数据格式，因为它能用对象、字段和数组表达结构化信息。

## 2. API Key 与 Access Token 有什么不同

| 概念 | 本质 | 常见特点 | 主要用途 |
|---|---|---|---|
| API Key | 应用身份标识 | 通常较长期、固定 | 识别哪个应用在调用服务 |
| Access Token | 一次授权得到的临时凭证 | 通常有时效，可带权限范围 | 代表某个用户或授权上下文访问资源 |

API Key 更像一张应用门禁卡：它告诉服务方“哪个应用来了”。

Access Token 更像一张临时通行证：它不仅证明身份，还可能限定“能访问什么、能做什么、什么时候过期”。

实际系统可能组合使用两者，也可能采用 OAuth、签名请求等更完整的机制。关键不是背名词，而是先问：**这个凭证代表谁，拥有什么权限，何时失效？**

## 3. 大模型里的 Token 是另一回事

在大模型语境中，Token 通常指文本被模型切分后的基本单位。它可以是一个词、一个字、一个词片段，甚至标点，具体取决于模型使用的分词方式。

所以：

- 认证 Token 关系到“你能不能调用”；
- 文本 Token 关系到“模型怎样处理输入，以及用量怎样计算”。

看到文档写“token 数量”时，要判断它说的是额度与文本长度，还是身份凭证。两者的安全含义完全不同。

## 4. 一个请求大致长什么样

下面只是结构示例，不对应真实服务：

```http
GET /v1/weather?city=Hong%20Kong HTTP/1.1
Authorization: Bearer YOUR_ACCESS_TOKEN
Accept: application/json
```

返回结果可能是：

```json
{
  "city": "Hong Kong",
  "temperature": 26,
  "unit": "celsius"
}
```

阅读这类结果时，先看最外层有哪些字段，再逐层进入对象或数组。对初学者来说，能在请求字段和返回字段之间建立对应关系，比急着背完整语法更重要。

## 5. 多模态又增加了什么

传统 API 可以只传文本或结构化字段，多模态应用则可能同时处理图像、语音、视频和文本。

它的价值在于信息互补：一张照片提供视觉内容，文字说明补充业务背景，结构化规则再约束输出格式。但输入类型增多后，也要更明确地设计校验、错误处理和人工复核，不能因为模型“看懂了”就默认结果一定正确。

## 6. 凭证安全是基本功

无论使用哪种 Key 或 Token，都应遵守几条底线：

1. 不把真实凭证写进公开笔记、截图、代码仓库或前端页面；
2. 示例统一使用 `YOUR_API_KEY` 等占位符；
3. 本地项目通过环境变量或安全的密钥管理方式读取；
4. 一旦泄露，立即撤销或轮换，而不是只删除公开文件；
5. 只授予完成任务所需的最小权限。

一句话总结：

> API Key 和 Access Token 解决“谁在调用、能做什么”；大模型的文本 Token 解决“内容怎样被切分和计量”。先分清问题，再选择概念。
