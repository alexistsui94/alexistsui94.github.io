<div class="seg">
<p class="en">Facing an important goal, / we usually ask: / “How do we make this succeed?” //</p>
</div>

<div class="seg">
<p class="en">Inversion / turns the question around: / “What would make it fail?” //</p>
</div>

<div class="seg">
<p class="en">This is not / about creating anxiety. // The paths to success / are usually many, / while the fatal errors / tend to be fewer, / more concentrated / and easier to spot. // Instead of imagining / a perfect plan, / start by removing / the risks that could / break the whole thing. //</p>
</div>

<h2>Why thinking backwards works better</h2>

<div class="seg">
<p class="en">The mathematician Jacobi / left a short piece of advice: / “Invert, always invert.” // Charlie Munger / applied the same habit / widely / to business, / investing / and life decisions. //</p>
</div>

<div class="seg">
<p class="en">It works / for three main reasons. //</p>
</div>

<div class="seg">
<p class="en">First, / avoiding big mistakes / is usually more achievable / than getting everything right. // A project needs / requirements, / data, / technology, / communication, / resources / and timing / to all line up. // To fail, / it may only need / one key assumption / to stay false / for a long time. //</p>
</div>

<div class="seg">
<p class="en">Second, / failure paths / expose the blind spots / of a positive plan. // When we discuss / only benefits / and ideal states, / optimism easily takes over. // Asking “how could this go bad” / forces us / to check / the constraints we ignored. //</p>
</div>

<div class="seg">
<p class="en">Third, / a lot of improvement / comes from subtraction. // Removing / one meaningless approval, / deleting / a duplicate data-entry step, / or naming / an interface nobody owns / often beats / adding another management action. //</p>
</div>

<h2>A three-step framework you can use today</h2>

<h3>Step 1. Write the goal concretely</h3>

<div class="seg">
<p class="en">Do not write / “deliver a good project” / or “improve operations”. // Define a result / you can judge. // For example: / go live with the core process / on the agreed date, / let key users / work independently, / and do not interrupt / normal business. //</p>
</div>

<div class="seg">
<p class="en">The vaguer the goal, / the more / the risk discussion / drifts into generalities. //</p>
</div>

<h3>Step 2. Assume it has already failed</h3>

<div class="seg">
<p class="en">This is the pre-mortem. // Before you act, / imagine you are / in the future / and the project has failed, / then ask: / “What most likely happened?” //</p>
</div>

<div class="seg">
<p class="en">For an enterprise system go-live, / common answers / might look like this. //</p>
</div>

<ul class="seg-list">
<li><span class="en">Scope kept changing, / so the team / could never freeze it. //</span></li>
<li><span class="en">Master data / was too weak, / so test results / did not represent real business. //</span></li>
<li><span class="en">Key users / did not give time, / so training and acceptance / became a formality. //</span></li>
<li><span class="en">Departments / used different definitions, / and nobody / could make the final call. //</span></li>
<li><span class="en">Cutover / had no rollback plan, / so a small fault / became a business outage. //</span></li>
</ul>

<div class="seg">
<p class="en">This list / is more useful / than “let’s all pay attention to risk”, // because it points / at specific mechanisms. //</p>
</div>

<h3>Step 3. Put a guard on each failure path</h3>

<div class="seg">
<p class="en">Every major risk / should map / to one action / you can take in advance. //</p>
</div>

<table class="seg-table">
<thead><tr><th>Failure path</th><th>Guard to build early</th></tr></thead>
<tbody>
<tr><td><span class="en">Requirements keep changing</span></td><td><span class="en">Agree a scope baseline, / change conditions / and a decision owner</span></td></tr>
<tr><td><span class="en">Data cannot support go-live</span></td><td><span class="en">Profile the data early, / run a trial migration / and business checks</span></td></tr>
<tr><td><span class="en">Users cannot or will not use it</span></td><td><span class="en">Involve key users / in blueprint, / UAT / and training design</span></td></tr>
<tr><td><span class="en">Nobody makes the final call</span></td><td><span class="en">Agree an escalation path, / an owner / and a response deadline</span></td></tr>
<tr><td><span class="en">Cutover hits normal business</span></td><td><span class="en">Design phased go-live, / monitoring / and a rollback plan</span></td></tr>
</tbody>
</table>

<div class="seg">
<p class="en">The output of inversion / is not “risk literature”. // It is / an owner, / a trigger condition / and a concrete action. //</p>
</div>

<h2>It also works for business and personal decisions</h2>

<div class="seg">
<p class="en">In business analysis, / besides asking / “why might this company grow”, / ask: / what would keep / cash flow, / customer demand / or competitive advantage / getting worse? // These questions / move our attention / from the story / to the evidence. //</p>
</div>

<div class="seg">
<p class="en">In personal choices, / besides / “how do I get the ideal result”, / ask: / which habits / would almost certainly damage / long-term health, / reputation / or room to choose? // Some problems / do not need / a cleverer technique — / they need us / to stop / doing obviously harmful things / again and again. //</p>
</div>

<h2>Three limits to keep in mind</h2>

<ol class="seg-list">
<li><span class="en">Inversion / is not pessimism. // It serves action — / it does not prove / that nothing is worth doing. //</span></li>
<li><span class="en">Do not list risks / without measures. // If the list / changes no plan, / it is only emotional output. //</span></li>
<li><span class="en">It cannot replace / positive creation. // Avoiding errors / reduces loss / but does not create new value. // The usual order / is: / propose a plan first, / then use inversion / to check the holes. //</span></li>
</ol>

<div class="seg">
<p class="en">For me, / the most practical line / is this. //</p>
</div>

<blockquote><div class="seg">
<p class="en">Do not only ask / how to succeed — / also ask / what would fail; // then cut off / the most fatal paths, / one by one. //</p>
</div></blockquote>

<p class="evidence">This is a general note on decision methods and is not investment advice.</p>
